# Multi-Agent Orchestration на базе Claude Code: разделение когнитивных ролей в LLM-пайплайнах без внешней инфраструктуры

## Введение: о чём этот документ

Этот документ описывает production-систему мультиагентной оркестрации, реализованную внутри Claude Code CLI. Система решает одну задачу: превратить описание фичи на естественном языке в готовый, провалидированный код, который соответствует конвенциям большого проекта (Next.js 10, React 17, TypeScript, 17 брендовых тем, 5-слойная архитектура).

Ключевая идея: **вместо одного LLM-вызова с гигантским промптом используется пайплайн из 8+ изолированных суб-агентов**, каждый из которых работает на подходящей модели (Opus / Sonnet / Haiku) и в подходящем когнитивном режиме. Агенты общаются через файлы в `.claude/sessions/` — без LangChain, без очередей, без баз данных, без внешних сервисов.

## Часть 1. Почему мультиагентность, а не один промпт

### Проблема: один LLM не может быть хорош во всём одновременно

Когда ты даёшь одному вызову LLM задачу "проанализируй кодовую базу, спланируй изменения, напиши код, проверь его, исправь ошибки и покажи результат" — ты просишь модель одновременно быть аналитиком, архитектором, разработчиком и QA. Это приводит к:

- **Размыванию фокуса.** Модель пытается быть "хорошей во всём" и оказывается посредственной в каждом аспекте.
- **Ошибкам ревью собственного кода.** LLM склонна не замечать собственные ошибки — confirmation bias.
- **Невозможности использовать разные модели.** Для планирования нужен deep reasoning (дорогой Opus), для написания кода хватает Sonnet, для прогона линтеров хватает Haiku. Один вызов = одна модель = переплата или недоплата.
- **Взрыву контекста.** Один промпт должен содержать и конвенции, и код, и план, и вопросы — контекст засоряется, модель теряет фокус.

### Решение: когнитивное разделение труда

Каждый агент получает:
- **Одну роль** (аналитик, архитектор, разработчик, валидатор, консультант)
- **Одну задачу** (исследуй, спланируй, напиши код, проверь, исправь)
- **Минимальный контекст** — только то, что нужно для его задачи
- **Подходящую модель** — Opus для размышлений, Sonnet для исполнения, Haiku для рутины

Агенты изолированы — каждый запускается с нуля, без доступа к контексту предыдущего. Вся коммуникация идёт через файлы в session-директории. Это исключает "заражение" контекста: архитектор не может влиять на разработчика иначе, как через написанный plan.md.

## Часть 2. Архитектура системы

### 2.2. Четыре типа файлов — четыре уровня абстракции

**Rules (`.claude/rules/`)** — конвенции проекта: TypeScript стиль, SCSS структура, GraphQL naming, Redux паттерны. Загружаются конкретными агентами при необходимости. Не привязаны к конкретной задаче — описывают "как мы пишем код в этом проекте".

**Agents (`.claude/agents/`)** — identity-файлы: "кто ты, как ведёшь себя, что знаешь". Каждый step-файл начинается с `read {project-root}/.claude/agents/{role}.md and adopt that identity`. Агент — это не модель, а когнитивная роль, которую модель принимает.

**Skills (`.claude/skills/`)** — переиспользуемые шаблоны для конкретных задач: как создать SCSS-модуль (9 обязательных breakpoint-файлов), как создать useQuery хук (4 файла с naming-конвенциями), как заскаффолдить компонент. Архитектор ссылается на скилл в плане: "Для задачи 3 — Follow skill: scss-module.md". Разработчик читает скилл и использует его как точный шаблон.

**Step-файлы (`.claude/commands/dev-steps/`)** — инструкции для конкретного шага пайплайна. Каждый файл определяет: какого агента загружать, в каком execution mode работать, что читать, что делать, что писать на выход. Step-файл — это "должностная инструкция" для конкретной фазы работы.

### 2.3. Почему skills вынесены отдельно от rules

**Rules** отвечают на вопрос "КАК писать код в этом проекте" — это ограничения и конвенции. Пример: "все типы заканчиваются на `Type`", "импорты в 8 группах с комментариями", "px() только в mq/ файлах".

**Skills** отвечают на вопрос "ЧТО именно написать для конкретного паттерна" — это шаблоны и рецепты. Пример: "чтобы создать SCSS модуль, создай 11 файлов в такой структуре с таким содержимым, где root class = имя папки".

Разделение критично потому что:
1. **Разные потребители.** Rules читают ВСЕ агенты (архитектор — при планировании, разработчик — при написании кода, ревьюер — при проверке). Skills читает только разработчик — и только те, которые архитектор указал в плане.
2. **Экономия контекста.** Если SCSS-модуль не нужен в задаче, разработчик не тратит токены на чтение scss-module.md (5KB+ шаблонного кода).
3. **Composability.** Одна задача может ссылаться на 3 скилла: "component-scaffold + scss-module + use-query-hook". Каждый скилл самодостаточен — это Lego-блок.

### 2.4. Оркестратор: thin dispatcher

`dev.md` — это **не** агент с ИИ-логикой. Это простой роутер:

1. Создаёт session-директорию
2. Запускает суб-агентов в правильном порядке
3. Читает файлы-результаты между шагами
4. Принимает решения о маршрутизации (есть блокеры? → запусти консультанта. Есть must-fix? → запусти фиксер)
5. Показывает пользователю checkpoint-информацию

Оркестратор НЕ анализирует код, НЕ пишет код, НЕ принимает архитектурных решений. Все "мозги" — в суб-агентах. Оркестратор — это if/else по содержимому файлов.

## Часть 3. Агенты и их когнитивные роли

### 3.1. Analyst (analyst.md)

| Параметр | Значение |
|----------|----------|
| **Модель** | Sonnet |
| **Когнитивный профиль** | Exploration + Question formulation |
| **Execution Mode** | MEDIUM |
| **Используется в** | Step 1 (Clarify), Step 2.5 (Preflight) |

**Что делает:** Исследует кодовую базу, идентифицирует затронутые файлы, формулирует уточняющие вопросы, собирает context-pack.

**Почему Sonnet, а не Opus:** Задача аналитика — широкий поиск и систематизация, а не глубокий reasoning. Sonnet отлично справляется с "прочитай 15 файлов и выпиши, что изменится", при этом стоит значительно дешевле. Глубокий анализ trade-offs не нужен — это задача архитектора.

**Ключевая особенность — Context Pack.** Аналитик создаёт `context-pack.md` — самодостаточный снимок всех релевантных файлов проекта. Этот файл читают ВСЕ последующие агенты вместо того, чтобы каждый читал исходники с диска. Один раз собрали — пять раз переиспользовали. Это сокращает количество tool-calls (Read файлов) на 60-80% по всему пайплайну.

Context Pack имеет жёсткий лимит в 80KB — если превышает, аналитик обрезает reference patterns и предупреждает. Это защита от взрыва контекста на больших задачах.

**Ключевая особенность — Forced Questions.** Аналитик ОБЯЗАН задать минимум 1 вопрос и предложить минимум 3 критерия успеха. Даже если задача кажется очевидной. Это заставляет пользователя валидировать понимание задачи ДО начала планирования, что предотвращает самую дорогую ошибку: реализацию не того, что просили.

### 3.2. Architect (architect.md)

| Параметр | Значение |
|----------|----------|
| **Модель** | Opus |
| **Когнитивный профиль** | Deep reasoning + Trade-off analysis |
| **Execution Mode** | HIGH |
| **Используется в** | Step 2 (Plan), Step 2.5b/3.5 (Consult), Step 4 (Review), Step 7B (Escalate) |

**Что делает:** Проектирует план реализации, ревьюит код, консультирует разработчика, диагностирует тупиковые ситуации.

**Почему Opus:** Архитектор принимает решения с последствиями. "Положить хук в bus/profile/ или core/hooks/?" — неправильный ответ приводит к нарушению архитектурных границ, которое потом сложно исправить. Opus на порядок лучше Sonnet в reasoning о trade-offs и последствиях. Это единственная роль, где экономия на модели прямо вредит качеству.

**Ключевая особенность — Self-contained Plan.** Архитектор создаёт `plan.md`, который является полностью самодостаточной инструкцией. Разработчику НЕ нужно читать другие файлы проекта, чтобы понять, что делать. В план включены: точные пути файлов, точные импорты (Import Map), точная структура SCSS, все необходимые типы. Это радикально отличается от "сделай компонент фильтра" — план больше похож на технический чертёж.

**Ключевая особенность — Naming Map.** Для каждой сущности план содержит каноническое имя на всех слоях: GraphQL operation → generated type → hook → directory → component → CSS class. Одно имя — один концепт. Разработчик НЕ принимает решений об именовании.

**Ключевая особенность — Множественные роли одного агента.** Architect — это одна identity (architect.md), но она используется в четырёх разных контекстах:
- **Planner** (Step 2) — пишет план с нуля
- **Consultant** (Step 2.5b / 3.5) — отвечает на конкретные вопросы
- **Reviewer** (Step 4) — критикует чужой код
- **Escalator** (Step 7B) — диагностирует тупик

Каждый контекст задаётся step-файлом, а не agent-файлом. Identity одна — поведение разное.

### 3.3. Developer (developer.md)

| Параметр | Значение |
|----------|----------|
| **Модель** | Sonnet |
| **Когнитивный профиль** | Mechanical execution |
| **Execution Mode** | LOW |
| **Используется в** | Step 3 (Implement), Step 5 (Fix), Step 7 (Fix Loop) |

**Что делает:** Пишет код строго по плану. Исправляет must-fix замечания ревью. Исправляет ошибки валидации.

**Почему Sonnet:** Разработчику намеренно НЕ нужен deep reasoning. План уже содержит все решения. Разработчик — это "руки", а не "мозг". Дать Opus на эту роль = переплата + риск того, что модель начнёт "улучшать" план (Opus склонен к over-engineering при отсутствии ограничений).

**Ключевая особенность — Execution Mode LOW.** Каждый step-файл объявляет свой "execution mode":
- **LOW:** механическое исполнение, минимальное thinking, никаких решений
- **MEDIUM:** сбалансированное исследование, фокус на фактах
- **HIGH:** глубокий reasoning, trade-offs, альтернативы

Execution Mode — это не технический параметр модели. Это инструкция в промпте, которая калибрует поведение: "ты НЕ думаешь об архитектуре, ты НЕ принимаешь решений, ты выполняешь буквально". Sonnet в LOW mode ведёт себя принципиально иначе, чем Sonnet в MEDIUM mode.

**Ключевая особенность — Mid-flight Consultation.** Разработчик имеет право остановиться и запросить консультацию у архитектора (Opus), если столкнулся с фактическим блокером: файл не существует, тип не совпадает, зависимость отсутствует. При этом:
- Триггеры жёстко ограничены 5 категориями (missing_file, missing_symbol, type_mismatch, missing_dependency, api_contract_mismatch)
- Максимум 1 консультация за сессию (hard cap)
- Разработчик пишет `midflight-consult-request.md` и ОСТАНАВЛИВАЕТСЯ — не пытается "обойти" проблему

Это решает проблему "Sonnet молча делает неправильно, потому что план разошёлся с реальностью".

**Ключевая особенность — Context Pack Delta.** После реализации разработчик создаёт `context-pack.delta.md` — снимок изменений (новые файлы целиком + unified diff для модифицированных). Все последующие агенты (ревьюеры, фиксеры, валидатор) читают delta вместо re-read файлов с диска. Каждый следующий шаг (Step 5, Step 7) ДОБАВЛЯЕТ свою секцию в delta — файл растёт append-only.

### 3.4. Validator (validator.md)

| Параметр | Значение |
|----------|----------|
| **Модель** | Haiku |
| **Когнитивный профиль** | Pattern matching + Report generation |
| **Execution Mode** | LOW |
| **Используется в** | Step 6 (Validate), Step 8 (Present) |

**Что делает:** Запускает `yarn typescript`, `yarn lint:ts`, `yarn lint:scss`. Парсит результаты. Пишет отчёт. НЕ исправляет ошибки.

**Почему Haiku:** Валидатор выполняет самую простую когнитивную работу в пайплайне: запустить bash-команду, отфильтровать вывод, посчитать строки, заполнить шаблон отчёта. Haiku справляется с этим идентично Opus, при этом стоит ~20x дешевле и работает быстрее.

**Ключевая особенность — Baseline Diff.** Валидатор не просто считает ошибки — он сравнивает текущие ошибки с baseline-ом (состояние `origin/main` до начала работы). Если в проекте уже было 200 TS-ошибок и стало 203 — в отчёт попадут только 3 новые (regressions), а не все 203. Это позволяет работать в legacy-кодовых базах с существующим техдолгом.

Baseline собирается в фоне при старте сессии (ещё на Step 1) и кэшируется по merge-base commit hash. Повторные запуски на том же бранче не перезапускают yarn 3 раза.

**Ключевая особенность — Cascade Detection.** Если TypeScript-ошибка в файле A каскадирует в 15 ошибок в файлах B-P — baseline diff ловит все 16 как новые. Filename-filter (fallback при отсутствии baseline) ловит только 1, потому что файлы B-P не в списке изменённых. Валидатор явно указывает mode (baseline-diff или filename-filter) в отчёте, чтобы downstream знал о reliability.

### 3.5. Consultant (architect.md в режиме consult)

| Параметр | Значение |
|----------|----------|
| **Модель** | Opus |
| **Когнитивный профиль** | Targeted problem-solving |
| **Execution Mode** | HIGH |
| **Используется в** | Step 2.5b (Preflight Consult), Step 3.5 (Mid-flight Consult) |

**Что делает:** Отвечает на конкретные вопросы от детектора блокеров (pre-flight) или от разработчика (mid-flight). Не пишет план, не ревьюит — только консультирует.

**Почему Opus:** Консультант должен быть не слабее планировщика. Если он на Sonnet — его ответ не добавит информации сверх того, что Sonnet-разработчик уже "знает". Opus-консультант может увидеть контекст, который Sonnet пропустил, и дать архитектурно корректный ответ.

**Ключевая особенность — PLAN_STATUS.** Каждый ответ консультанта содержит сигнал о состоянии плана:
- `OK` — план корректен, вопросы решены, разработчик может продолжать
- `PLAN_PATCH` — план в целом верен, но нужны точечные правки (другой путь импорта, отсутствующий тип). Консультант пишет конкретный патч.
- `PLAN_BROKEN` — план фундаментально неверен (API не поддерживает то, что план предполагает). Оркестратор перезапускает Step 2 с feedback-ом.

Это позволяет системе корректно реагировать на три уровня проблем: мелкие (патч), средние (коррекция), фатальные (replan).

## Часть 4. Пайплайн: пошаговый разбор

### Полная схема потока

```
Пользователь
  │
  ▼
Step 1: CLARIFY (Analyst, Sonnet)
  │  → questions.md, context-pack.md
  │  ← user-answers.md
  ▼
Step 2: PLAN (Architect, Opus)
  │  → plan.md
  │  ← user confirmation
  ▼
Step 2.5a: PREFLIGHT (Analyst, Sonnet)
  │  → preflight-blockers.md
  │  STATUS: clear → Step 3
  │  STATUS: blocked ↓
  │
  ▼
Step 2.5b: CONSULT (Architect, Opus) [conditional]
  │  → preflight-consult-response.md
  │  PLAN_STATUS: OK/PATCH → Step 3
  │  PLAN_STATUS: BROKEN → re-run Step 2 (max 1x)
  ▼
Step 3: IMPLEMENT (Developer, Sonnet)
  │  → code changes, context-pack.delta.md
  │  [optional: midflight-consult-request.md → STOP]
  │
  ├─ mid-flight blocker? ─→ Step 3.5: CONSULT (Opus) → re-launch Step 3
  │
  ▼
Step 4: REVIEW (3x Architect, Opus) [parallel]
  │  4A: Architecture boundaries
  │  4B: TypeScript + naming consistency
  │  4C: SCSS conventions (if .scss changed)
  │  → review-arch.md, review-ts.md, review-scss.md
  │  must-fix = 0 → Step 6
  │  must-fix > 0 ↓
  ▼
Step 5: FIX (Developer, Sonnet)
  │  → fix-log.md, delta update
  ▼
Step 6: VALIDATE (Validator, Haiku)
  │  → validate-log.md
  │  all clean → Step 8
  │  errors ↓
  ▼
Step 7: FIX LOOP (Developer, Sonnet) [max 3 iterations]
  │  → fix-loop-log.md, delta update
  │  re-run Step 6
  │  still failing after 3x ↓
  ▼
Step 7B: ESCALATE (Architect, Opus)
  │  → escalation.md
  │  APPLY → Step 7 once more → Step 6
  │  CONFIRM → user input → Step 7 → Step 6
  │  ABORT → stop
  ▼
Step 8: PRESENT (Validator, Haiku)
  │  → summary.md
  ▼
Пользователю показывается итоговый summary
```

### Step 1 — CLARIFY (Analyst, Sonnet)

**Вход:** Описание задачи от пользователя.
**Выход:** `spec.md`, `questions.md`, `context-pack.md`.

Аналитик выполняет три задачи:

1. **Исследует кодовую базу.** Определяет какие домены затронуты (bus/profile? bus/auth? core/hooks?), какие файлы нужно изменить, какие новые файлы создать. Проверяет архитектурные ограничения — не нарушит ли задача 5-слойную границу.

2. **Формулирует вопросы.** Каждый вопрос — про скоуп, edge-case или неоднозначность. "Это для одной темы или для всех 17?", "Должен ли фильтр работать на мобильных breakpoints?", "Сохранять ли состояние фильтра при переходе между страницами?"

3. **Собирает context-pack.** Читает все affected-файлы с диска и упаковывает в один markdown. Downstream-агенты читают этот файл вместо десятков отдельных Read-вызовов.

**Пользовательский checkpoint:** Оркестратор показывает пользователю Understanding + Questions. Пользователь отвечает. Ответы записываются в `user-answers.md`. Только после этого запускается планирование.

### Step 2 — PLAN (Architect, Opus)

**Вход:** `spec.md`, `context-pack.md`, `user-answers.md`.
**Выход:** `plan.md` — полностью самодостаточный blueprint.

Архитектор создаёт план такой детализации, что разработчик, который никогда не видел эту кодовую базу, может реализовать задачу, следуя плану пошагово. План содержит:

- **Success Criteria** — 3-5 проверяемых семантических целей (не "TypeScript компилится", а "пользователь видит бейдж с суммой кредитов + бонусов")
- **Architecture Decision** — почему выбран этот подход, а не альтернативы
- **Naming Map** — каноническое имя сущности на всех слоях
- **Ordered Tasks** — пошаговые инструкции с точными путями и кодом
- **Import Map** — точные импорты для каждого файла
- **SCSS Structure** — какие файлы стилей создать
- **Required Reading** — какие skills и rules разработчик должен прочитать
- **Validation Checklist** — что проверить после реализации

**Пользовательский checkpoint:** Оркестратор показывает краткий summary плана. Пользователь подтверждает или просит изменения. При изменениях — feedback записывается в `plan-feedback.md`, Step 2 перезапускается.

### Step 2.5 — PREFLIGHT (Analyst → conditional Architect)

**Вход:** `plan.md`, `context-pack.md`.
**Выход:** `preflight-blockers.md`, опционально `preflight-consult-response.md`.

Это "предполётная проверка". Sonnet-аналитик читает план и проверяет каждую задачу на фактическую выполнимость:

- Файл из плана существует? (или план говорит "create" для существующего?)
- Импорт из плана доступен в указанном модуле?
- Тип из `__generated__/` совпадает с тем, что план предполагает?
- Hook/helper/component из плана не deprecated?

Если всё чисто — `STATUS: clear`, пайплайн идёт дальше. Если найдены блокеры — запускается Opus-консультант, который отвечает на конкретные вопросы. Консультант может вернуть `PLAN_PATCH` (точечные правки) или `PLAN_BROKEN` (фундаментальная проблема → re-plan).

**Зачем нужен этот шаг:** Без preflight разработчик (Sonnet) молча делает "best effort" когда план не совпадает с реальностью — и ошибки ловятся только на Step 4 (review). Один Opus-вызов на preflight экономит целый цикл implement → review → fix.

### Step 3 — IMPLEMENT (Developer, Sonnet)

**Вход:** `plan.md`, `context-pack.md`, skill-файлы, опционально `preflight-consult-response.md`.
**Выход:** Код на диске, `context-pack.delta.md`.

Разработчик читает план и выполняет задачи строго по порядку. Для каждой задачи:
- Если `create` — Write новый файл с точным содержимым из плана
- Если `modify` — Read файл с диска, Edit нужные строки

Каждый скилл из Required Reading читается ровно один раз. Скилл содержит точный шаблон кода — разработчик подставляет значения из плана (имена, пути, типы) и получает файл.

**Mid-flight consultation trigger:** Если разработчик обнаруживает, что файл из плана не существует (или тип не совпадает, или зависимость отсутствует) — он записывает `midflight-consult-request.md` с номером задачи, на которой застрял, категорией проблемы и конкретным вопросом. Затем останавливается. Оркестратор запускает Opus-консультанта, получает ответ и перезапускает Step 3 — разработчик читает ответ и продолжает с задачи, на которой остановился.

### Step 4 — REVIEW (3x Architect, Opus, параллельно)

**Вход:** `plan.md`, `context-pack.md`, `context-pack.delta.md`, `diff.txt`.
**Выход:** `review-arch.md`, `review-ts.md`, `review-scss.md`.

Три независимых ревьюера запускаются параллельно:

**4A — Architecture Review:** Проверяет import boundaries (5-слойная матрица), layer placement (hook в правильном домене?), file structure (styles/index.module.scss?), consistency с планом (ничего не добавлено/пропущено).

**4B — TypeScript & Naming Review:** Проверяет naming consistency (entity name одинаковое на всех слоях), TypeScript style (нет `as`, нет `interface`, нет `enum`, все типы с `Type` suffix), import order (8 групп с комментариями).

**4C — SCSS Review** (только если изменены .scss файлы): Проверяет px() placement (только в mq/), palette usage (нет raw hex), root class naming (= folder name), nesting depth (max 3).

Каждый ревьюер использует протокол severity: **must** (блокер, обязательно исправить), **imho** (не блокер, рекомендация), **note** (вопрос/наблюдение). Только must-fix замечания требуют исправления.

**Оптимизация: shared diff.** Оркестратор заранее запускает `git diff > diff.txt`. Все три ревьюера читают один файл вместо того, чтобы каждый запускал `git diff` сам. 3 вызова git → 1.

**Оптимизация: stable cache prefix.** Reading Order всех трёх ревьюеров начинается с одних и тех же стабильных файлов (CLAUDE.md, rules, .context, plan.md). Это позволяет prompt cache переиспользовать общий префикс, снижая latency и стоимость при параллельном запуске.

### Step 5 — FIX (Developer, Sonnet)

**Вход:** `review-arch.md`, `review-ts.md`, `review-scss.md`, `context-pack.delta.md`.
**Выход:** Исправленный код, `fix-log.md`, обновлённый delta.

Если Step 4 нашёл must-fix замечания — разработчик исправляет только их. Ничего больше. Каждый fix — хирургический: прочитать файл, поменять конкретную строку, перейти к следующему. Если must-fix замечаний нет — шаг пропускается полностью.

### Step 6 — VALIDATE (Validator, Haiku)

**Вход:** Изменённые файлы, baseline (если есть).
**Выход:** `validate-log.md`.

Запуск трёх инструментов:
1. `yarn typescript` — TypeScript type checking
2. `yarn lint:ts` — ESLint
3. `yarn lint:scss` — Stylelint (только если есть .scss в diff)

Результат сравнивается с baseline. В отчёт попадают только NEW ошибки (regressions). Если new errors = 0 — переход к Step 8 (present). Если > 0 — переход к Step 7 (fix loop).

### Step 7 — FIX LOOP (Developer, Sonnet, max 3 итерации)

**Вход:** `validate-log.md`.
**Выход:** Исправленный код, `fix-loop-log.md`.

Циклическая отработка: исправить ошибки → перевалидировать → ещё ошибки? → исправить → перевалидировать. Максимум 3 итерации.

Каждая итерация — отдельный запуск суб-агента. Разработчик читает validate-log, применяет стандартные fix-паттерны (TS2322 → type annotation, no-unused-vars → remove import, import/order → reorder).

Если через 3 итерации ошибки остаются — эскалация, а не бесконечный цикл.

### Step 7B — ESCALATE (Architect, Opus)

**Вход:** `plan.md`, `validate-log.md`, `fix-loop-log.md`, failing source files.
**Выход:** `escalation.md`.

Архитектор включается когда Sonnet-разработчик застрял. Задача — найти root cause: почему фиксы не работают? Типичные диагнозы:
- Одна и та же ошибка повторяется → upstream тип неверен → нужно менять план
- Cascade root cause → одно изменение разблокирует 10 ошибок
- Оригинальный Architecture Decision был неправильным → нужен другой подход

Архитектор НЕ правит код — пишет диагноз и revised approach. Оркестратор маршрутизирует:
- **APPLY** — пусть разработчик применит revised approach
- **CONFIRM** — покажи пользователю и дождись подтверждения
- **ABORT** — задача нереализуема в текущем скоупе

Hard cap: Step 7B запускается максимум 1 раз за сессию.

### Step 8 — PRESENT (Validator, Haiku)

**Вход:** Все артефакты сессии.
**Выход:** `summary.md`.

Финальная сводка: что было сделано, какие файлы созданы/изменены, статус ревью и валидации, success criteria с оценкой (CODE OK / CODE UNCLEAR / CODE MISSED), что нужно проверить вручную.

Haiku используется потому что это чисто текстовая трансформация: прочитай 8 файлов, извлеки ключевые факты, заполни шаблон. Zero reasoning required.

## Часть 5. Паттерны оркестрации

### 5.1. Sequential Pipeline

Основной поток: Step 1 → 2 → 2.5 → 3 → 4 → 5 → 6 → 7 → 8. Каждый шаг зависит от артефактов предыдущего. Оркестратор читает файл-результат и решает, что делать дальше.

### 5.2. Parallel Fan-out

Step 4 запускает 3 ревьюера одновременно (Architecture, TypeScript, SCSS). Они независимы — каждый проверяет свой аспект, каждый пишет в свой файл. Оркестратор ждёт завершения всех трёх, затем агрегирует must-fix.

### 5.3. Conditional Branching

- Preflight: `STATUS: clear` → skip consult, `STATUS: blocked` → launch consult
- Review: must-fix = 0 → skip Step 5, must-fix > 0 → launch Step 5
- Validate: all clean → skip fix loop, errors → launch Step 7
- SCSS files in diff → launch 4C, no SCSS → skip 4C
- Consult `PLAN_STATUS: PLAN_BROKEN` → re-run Step 2

Вся маршрутизация — по содержимому файлов. Оркестратор grep-ает STATUS/PLAN_STATUS, считает must-fix, проверяет существование файлов.

### 5.4. Mid-flight Escalation

Новый паттерн. Разработчик (Sonnet, Step 3) может прервать себя и запросить помощь у архитектора (Opus, Step 3.5). Механизм:

1. Developer пишет `midflight-consult-request.md` с `LAST_COMPLETED_TASK: N-1`
2. Developer ОСТАНАВЛИВАЕТСЯ
3. Оркестратор замечает файл-запрос без файла-ответа
4. Запускает Opus-консультанта
5. Консультант пишет `midflight-consult-response.md`
6. Оркестратор перезапускает Step 3
7. Developer читает response + свой delta, продолжает с задачи N

Hard cap: 1 mid-flight consultation per session.

### 5.5. Loop with Circuit Breaker

Step 6 → Step 7 → Step 6 → Step 7 → Step 6 → Step 7 → Step 7B. Максимум 3 итерации fix loop. Если ошибки остаются — circuit breaker: эскалация к Opus-архитектору (Step 7B), который предлагает другой подход. Если и после этого не помогло — эскалация к пользователю.

## Часть 6. Коммуникация между агентами: файловый протокол

### Почему файлы, а не "shared memory" или API?

1. **Debuggability.** Открыл `.claude/sessions/dev-20260414-175648/` → видишь всё, что произошло. Каждый файл — артефакт конкретного шага. Можно посмотреть plan.md, увидеть что архитектор задумал. Посмотреть review-ts.md, увидеть что ревьюер нашёл. Это как git log для пайплайна.

2. **Reproducibility.** Session-директория — полный snapshot. Если что-то сломалось — перезапусти конкретный step с теми же input-файлами, получишь ту же диагностику. Попробуй воспроизвести баг в LangChain pipeline с shared memory.

3. **Isolation.** Каждый агент — новый sub-agent без контекста предыдущего. Единственный способ "общаться" — через файлы. Это исключает contamination: архитектор не может случайно повлиять на разработчика через residual context.

4. **Version control.** Session-файлы в `.claude/sessions/` — gitignored (не засоряют репозиторий), но живут на диске для аудита. При желании можно git add конкретную сессию и закоммитить как documentation artifact.

5. **Prompt cache efficiency.** Файлы читаются в стабильном порядке (Reading Order). Файлы, общие для нескольких агентов (rules, conventions), всегда идут первыми. Это позволяет Claude Code's prompt cache переиспользовать общий префикс.

### Формат артефактов

Все файлы — markdown. Без JSON, без YAML, без custom formats. Markdown потому что:
- LLM нативно генерирует и парсит markdown
- Человек может открыть и прочитать
- Структура (headers, lists, code blocks) достаточна для routing

Каждый артефакт имеет предсказуемую структуру, заданную в step-файле. Оркестратор знает, что `preflight-blockers.md` содержит строку `STATUS:` на второй строке, а `review-arch.md` содержит секцию `## must-fix`.

### Context Pack + Delta: snapshot + patch

Вместо того чтобы каждый агент читал 15 файлов с диска (15 tool calls × 5 агентов = 75 tool calls), используется двухчастная система:

- `context-pack.md` — snapshot "до" (создаётся Step 1, читается всеми)
- `context-pack.delta.md` — patch "после" (создаётся Step 3, append Step 5/7)

Pack + Delta = полная картина кода на любом этапе пайплайна. Один Read вместо пятнадцати.

## Часть 7. Prompt Cache и Token Optimization

### Reading Order как cache strategy

Каждый step-файл декларирует Reading Order — порядок чтения файлов. Это не формальность. Порядок спроектирован так, чтобы стабильные файлы (rules, conventions, agent identity) читались первыми, а volatile (validate-log, review results) — последними.

Claude Code реализует prompt caching с TTL ~5 минут. Если два агента читают файлы в одинаковом порядке в пределах 5 минут — второй получает cache hit на общем префиксе. Step 4 запускает 3 ревьюера параллельно — все трое начинают с тех же rules → prompt cache.

Step 7 (fix loop) запускается до 3 раз. Каждый раз Reading Order одинаковый — только validate-log.md меняется в конце. 80% промпта = cache hit.

### Execution Mode как token saver

LOW mode в промпте разработчика: "Intent: mechanical execution — no architectural decisions, no improvisation. Thinking: minimal." Это не только поведенческая инструкция — модель с LOW mode генерирует меньше reasoning tokens и фокусируется на tool calls (Read/Edit). Opus в HIGH mode тратит 3-5x больше thinking tokens, чем Sonnet в LOW mode — разница ощутима на 10+ step-файлах за сессию.

### Model routing как cost optimization

| Роль | Модель | ~Стоимость / задачу | Обоснование |
|------|--------|---------------------|-------------|
| Analyst | Sonnet | $$ | Широкий поиск, не нужен deep reasoning |
| Architect | Opus | $$$$ | Решения с последствиями, trade-offs |
| Developer | Sonnet | $$ | Механическое исполнение по плану |
| Validator | Haiku | $ | Запуск команд + парсинг output |
| Consultant | Opus | $$$$ (conditional) | Нужен не слабее планировщика |

Если бы весь пайплайн работал на Opus — стоимость ~10x выше. Если бы весь на Sonnet — качество планов и ревью падает, Step 7 loop чаще, общая стоимость парадоксально растёт (больше итераций).

## Часть 8. Без внешней инфраструктуры — что это значит

### Что используется

- **Claude Code CLI** — runtime для агентов (tool calls: Read, Write, Edit, Bash, Glob, Grep, Agent)
- **Файловая система** — хранение артефактов (`.claude/sessions/`)
- **Git** — baseline для валидации, diff для review
- **yarn** — запуск проектных линтеров (typescript, eslint, stylelint)
- **Markdown** — формат коммуникации

### Что НЕ используется

- LangChain / LangGraph / LlamaIndex — не нужен фреймворк для оркестрации, файлы + if/else достаточно
- CrewAI / AutoGen / Swarm — не нужен "agent framework", Claude Code Agent tool — нативная альтернатива
- Vector databases — не нужен RAG, context-pack решает ту же задачу в рамках одной сессии
- Redis / PostgreSQL / Queue — не нужна shared memory, файлы самодостаточны
- Custom API server — не нужен backend, Claude Code запускается локально
- Docker / Kubernetes — не нужен infra, всё в терминале

### Что это даёт

1. **Zero setup.** `git clone` + `.claude/` уже в репозитории. Новый разработчик запускает `/dev <задача>` и получает тот же пайплайн.
2. **Version controlled.** Весь пайплайн (step-файлы, agent-файлы, skills, rules) — это код. PR, ревью, blame, history — стандартный git workflow.
3. **Debuggable.** Каждый session-артефакт — markdown файл. `cat plan.md` → видишь что архитектор спланировал. `cat review-ts.md` → видишь что ревьюер нашёл. Попробуй это с LangChain trace.
4. **Modifiable.** Хочешь добавить step? Создай markdown файл, добавь маршрут в оркестратор. Хочешь изменить поведение? Отредактируй step-файл. Хочешь другую модель? Поменяй `model: "sonnet"` на `model: "opus"` в одной строке.
5. **Portable.** Структура не привязана к конкретному проекту. Замени rules/ и skills/ — и пайплайн работает на другой кодовой базе.

## Часть 9. Пример реальной сессии

Сессия `dev-20260414-175648`: исправление отсутствующего бейджа кредитов в мобильном хедере uaBrides.

**Step 1 (Analyst, Sonnet):** Аналитик исследовал кодовую базу, нашёл что в natalyDate баланс (`credits + bonuses`) вычисляется и передаётся в `counterCreator`, а в uaBrides этот механизм отсутствует. Сформулировал вопросы о scope (только uaBrides?), поведении при нулевом балансе, необходимости серверной загрузки данных. Собрал context-pack из 6 файлов.

**Step 2 (Architect, Opus):** Спланировал 2 задачи: (1) добавить вычисление `balance` в `index.tsx` uaBrides хедера, (2) добавить `balance` в `PropsType` и `counterCreator` в `prepareLists.ts`. Import Map, Naming Map — всё в плане.

**Step 3 (Developer, Sonnet):** Выполнил обе задачи. Создал delta с diff-ами.

**Step 4 (2x Architect, Opus, параллельно):** Architecture: PASS. TypeScript/Naming: PASS. SCSS review пропущен (нет .scss в diff).

**Step 6 (Validator, Haiku):** `yarn typescript` — 0 new errors. `yarn lint:ts` — 0 new errors. Stylelint — skipped.

**Step 8 (Validator, Haiku):** Summary с 3 success criteria, все CODE OK. Manual verification: проверить визуально на мобильном breakpoint.

**Результат:** Задача от описания до провалидированного кода — без ручного кодирования, с двумя пользовательскими checkpoint-ами (ответы на вопросы, подтверждение плана).

## Часть 10. Итоги

### Что мы получили

1. **Когнитивное разделение труда.** Каждый агент оптимален для своей задачи — нет "универсального солдата", есть специалисты.
2. **Model routing.** Opus только там, где нужен reasoning. Sonnet для execution. Haiku для рутины. Стоимость ~3-5x ниже, чем "всё на Opus".
3. **Файловый протокол.** Debuggable, reproducible, version-controlled. Артефакт каждого шага — markdown на диске.
4. **Circuit breakers.** Hard caps на каждый цикл (3 fix iterations, 1 escalation, 1 mid-flight consult, 1 re-plan). Система не уходит в бесконечный loop.
5. **Zero infrastructure.** Claude Code CLI + файлы + git. Ничего больше.
6. **Composability.** Step-файлы, agent-файлы, skills, rules — всё модульное. Добавить шаг = создать markdown + обновить роутер.

### Для кого это работает

Для команд с жёсткими конвенциями, большой кодовой базой и повторяющимися паттернами (создание компонентов, хуков, страниц). Чем больше конвенций в rules/ и шаблонов в skills/ — тем выше ROI пайплайна.
