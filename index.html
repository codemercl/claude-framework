Конфликт режимов мышления

Планирование требует deep reasoning, а написание кода — механического исполнения. Совмещение в одном вызове приводит к тому, что модель «переключается» между ролями и теряет контекст решений.

👁

Ревью собственного кода

Модель, написавшая код, не находит в нём ошибок — confirmation bias. Изолированный ревьюер без контекста реализации ловит проблемы, которые автор пропускает.

💰

Нет выбора модели под задачу

Архитектурное решение требует Opus. Написание кода по готовому плану — Sonnet. Прогон линтера — Haiku. Один вызов = одна модель = переплата или недостаточное качество.

💣

Взрыв контекста

Конвенции проекта + код 15 файлов + план + вопросы пользователя в одном промпте. Релевантная информация тонет в шуме, качество генерации падает.

4 слоя системы

Rules

.claude/rules/

Конвенции проекта. TypeScript, SCSS, GraphQL, Redux. Читают ВСЕ агенты. Отвечают на вопрос «КАК писать код».

Agents

.claude/agents/

Identity-файлы. «Кто ты, как себя ведёшь». Analyst, Architect, Developer, Validator. Загружаются в начале каждого step.

Skills

.claude/skills/

Переиспользуемые шаблоны кода. SCSS-модуль, useQuery хук, компонент. Читает только Developer по ссылке из плана.

Steps

.claude/commands/dev-steps/

Инструкция для конкретного шага. Какой агент, какой mode, что читать, что писать на выход.

Skills vs Rules: Rules = ограничения («как»), Skills = рецепты («что именно написать»). Разные потребители, экономия контекста.

Steps 1-2: Понимание и планирование

Sonnet Step 1: Clarify

Analyst исследует кодовую базу. Определяет затронутые файлы и домены. Формулирует вопросы. Предлагает критерии успеха.

context-pack.md questions.md forced questions

Context Pack: снимок всех файлов в один markdown. Downstream читают его вместо десятков Read-вызовов. Лимит 80KB.

Opus Step 2: Plan

Architect создаёт самодостаточный blueprint. Разработчику НЕ нужно читать другие файлы проекта, чтобы понять, что делать.

Naming Map Import Map Ordered Tasks Success Criteria

Одно имя — один концепт на всех слоях: GraphQL operation → type → hook → directory → component → CSS class.

Steps 2.5 + 3.5: Консультации

Pre-flight Step 2.5

Sonnet-аналитик проверяет план на выполнимость ДО написания кода. Файл существует? Тип совпадает? Зависимость доступна?

STATUS: clear → Step 3
STATUS: blocked → Opus Consult
PLAN_BROKEN → Re-plan (max 1x)
Mid-flight Step 3.5

Developer обнаруживает блокер во время реализации. Пишет consult-request и ОСТАНАВЛИВАЕТСЯ. Opus отвечает, Developer продолжает.

5 триггеров: missing_file,
missing_symbol, type_mismatch,
missing_dependency, api_mismatch
Hard cap: 1 раз за сессию

Steps 4-7: Ревью, фикс, валидация

3x Opus

Review

3 ревьюера параллельно: Architecture boundaries, TypeScript/Naming, SCSS. Shared diff.txt — 1 вызов git вместо 3.

Severity: must / imho / note

Sonnet

Fix

Хирургические исправления только must-fix. Ничего больше. Если 0 must-fix — шаг пропускается.

Haiku

Validate

yarn typescript + lint:ts + lint:scss. Baseline diff: показывает только NEW ошибки, не legacy. Cascade detection.

Sonnet Opus

Fix Loop

Max 3 итерации Sonnet. Если застрял — Opus-эскалация (Step 7B): диагноз + revised approach.

Circuit breaker: 3 loops + 1 escalation

Паттерны оркестрации

Sequential

Основной поток. Каждый шаг читает артефакты предыдущего.

1 → 2 → 2.5 → 3 → ... → 8

Parallel Fan-out

3 ревьюера одновременно. Независимы, пишут в разные файлы.

   ┌ 4A: Arch
3 →├ 4B: TS     → 5
   └ 4C: SCSS

Conditional

Маршрутизация по содержимому файлов. STATUS, PLAN_STATUS, must-fix count.

clear → skip consult
0 must → skip fix
no scss → skip 4C

Mid-flight Escalation

Developer останавливается, Opus консультирует, Developer продолжает.

3 → STOP → Opus → 3'

Loop + Circuit Breaker

Fix → Validate цикл, max 3x. Затем эскалация к Opus.

6↔7 ↔ 6↔7 ↔ 6↔7 → 7B

Почему файлы?

Debuggable — открыл папку сессии, видишь весь ход работы

Reproducible — перезапусти шаг с теми же input-файлами

Isolated — нет contamination через shared memory

Cache-friendly — стабильный Reading Order = prompt cache hit

Context Pack + Delta

Pack = snapshot «до» (Step 1)
Delta = patch «после» (Step 3, append 5/7)

1 Read вместо 15. Все агенты читают одни файлы.

Model Routing: стоимость и качество

Роль Модель Cost Execution Mode Обоснование
Analyst Sonnet $$ MEDIUM Широкий поиск, не нужен deep reasoning
Architect Opus $$$$ HIGH Решения с последствиями, trade-offs
Developer Sonnet $$ LOW Механическое исполнение по плану
Validator Haiku $ LOW Запуск bash + парсинг output
Consultant Opus $$$$ HIGH Conditional — не слабее планировщика

Весь пайплайн на Opus = ~10x дороже. Весь на Sonnet = больше итераций fix loop, парадоксально дороже.
Reading Order + prompt cache TTL 5 мин = cache hit на параллельных ревьюерах.

Почему не BMAD, Kiro, LangChain?

BMAD Method

Агенты «общаются» друг с другом через длинные текстовые сообщения — имитация совещания. Выглядит красиво, но каждое «обсуждение» — это сотни токенов на форматирование, вежливость и пересказ контекста, который агент уже имеет.

Визуальная имитация коммуникации ≠ полезная работа. Токены тратятся на церемонию, а не на результат.

Kiro / Spec-driven

Генерирует спецификации и task-файлы, но нет разделения моделей по ролям — всё на одной модели. Нет параллельного ревью, нет mid-flight консультаций, нет circuit breaker при зацикливании.

Spec-first подход правильный, но без когнитивного разделения — это просто structured prompting.

LangChain / CrewAI

Внешняя инфраструктура: Python runtime, pip-зависимости, custom server. Агенты обмениваются через shared memory — невозможно открыть файл и посмотреть, что произошло. Отладка через trace viewer.

Фреймворк решает задачу оркестрации, но создаёт задачу инфраструктуры. Наш подход: 0 зависимостей.

Наш подход: файлы + Claude Code CLI

Нет имитации общения — агенты не «разговаривают». Один пишет файл, другой читает. Ноль токенов на церемонию.

Debuggable — открыл .claude/sessions/, видишь каждый артефакт каждого шага. cat plan.md — и ты знаешь, что решил архитектор.

Zero setup — git clone, и пайплайн уже в репозитории. Новый разработчик запускает /dev <задача> и получает тот же flow.
